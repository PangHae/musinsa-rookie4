**주요 발견:**

- **정확성 위반 0건**: 정원 초과가 절대 발생하지 않음

## 수용 가능 동시 접속자 분석

### 최대 동시 접속자 수 (추정)

| 구성 | 동시 접속자 | 설정 | 병목 지점 |
|------|-----------|------|----------|
| **단일 프로세스 (uvicorn)** | ~200-300명 | pool_size=50, max_overflow=30 | 이벤트 루프 / DB 풀 |
| **멀티 프로세스 (gunicorn 4w)** | ~800-1,200명 | 워커 4개 × 연결 80개 | CPU 코어 수 |
| **멀티 프로세스 (gunicorn 8w)** | ~1,500-2,000명 | 워커 8개 × 연결 80개 | DB max_connections |

### 제한 요소

1. **DB 커넥션 풀**: 각 워커가 독립 풀을 유지. `pool_size=50 + max_overflow=30 = 80`개 연결/워커, 4개 워커 시 최대 320개 연결. MariaDB 기본 `max_connections`는 151이므로 멀티 워커 구성 시 반드시 상향 조정 필요.

2. **비관적 잠금 경합**: 동일 강좌에 다수의 학생이 등록 시 `FOR UPDATE`가 직렬화. 정원 초과를 방지하는 올바른 동작이나, 인기 강좌의 쓰기 처리량을 제한. 동일 강좌에 500건 동시 등록 시 ~746 rps.

3. **CPU 바운드 작업**: Python GIL로 인해 단일 프로세스 병렬성 제한. Gunicorn 멀티 워커로 별도 프로세스를 통해 우회.

## 서버 구성

### 개발 환경 (단일 프로세스)
```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

### 프로덕션 환경 (멀티 프로세스)
```bash
gunicorn app.main:app -c gunicorn.conf.py
```

`gunicorn.conf.py` 설정:
- `workers = min(cpu_count * 2 + 1, 8)` (UvicornWorker 사용)
- `max_requests = 2000` + 지터 (메모리 누수 방지를 위한 워커 재활용)
- `timeout = 60초`
- `keepalive = 5초`

### 데이터베이스 튜닝 (프로덕션 권장)
```sql
SET GLOBAL max_connections = 500;
SET GLOBAL innodb_lock_wait_timeout = 10;
```

## 결론

서버는 단일 프로세스 모드에서 **500건 이상의 동시 요청**을 데이터 무결성 위반 없이 처리할 수 있다. Gunicorn 멀티 워커 배포를 사용하면 하드웨어에 따라 **1,000~2,000명의 동시 접속자**까지 확장 가능하다. 비관적 잠금 전략은 동일 강좌 행에 대한 쓰기를 직렬화하는 대가로 정확성(정원 초과 불가)을 보장하며, 이는 수강신청 시스템에 적합한 트레이드오프이다.
