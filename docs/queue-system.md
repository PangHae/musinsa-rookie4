# 대기열 시스템

## 대기열 시스템이란?

서버가 한 번에 처리할 수 있는 요청 수에는 한계가 있습니다. 대기열 시스템은 한꺼번에 몰리는 요청을 **줄 세워서** 서버가 감당할 수 있는 속도로 하나씩 처리하는 구조입니다.

```
[사용자 1000명] → 동시 요청 → 서버 죽음  ❌

[사용자 1000명] → 대기열 → 서버가 감당 가능한 속도로 처리  ✅
```

수강신청처럼 **특정 시간에 트래픽이 폭발**하는 시스템에서 핵심입니다.

---

## 대기열 없는 현재 구조의 문제

```
수강신청 오픈 순간:
학생 10,000명 → 동시에 POST /enrollments
                → DB에 SELECT FOR UPDATE 10,000개 동시
                → Lock 대기 폭발 → 응답 수십 초 → 타임아웃 → 서버 다운
```

---

## 대기열 구현 방법 3가지

### 방법 1: DB 기반 대기열 (간단, 느림)

요청이 오면 DB의 `queue` 테이블에 INSERT만 하고 즉시 응답합니다. 별도 워커가 순서대로 꺼내서 처리합니다.

```
[학생] → POST /enrollments
         └→ queue 테이블에 INSERT (빠름)
         └→ "접수 완료, 순번 523번입니다" 즉시 응답

[백그라운드 워커]
  └→ queue 테이블에서 1건씩 꺼내 실제 수강신청 처리
  └→ 결과를 결과 테이블에 저장

[학생] → GET /enrollments/status/523
         └→ "처리 중" or "성공" or "정원 초과"
```

**장점**: 추가 인프라 불필요
**단점**: 폴링이 필요하고 실시간성이 낮음, DB 부하 있음

---

### 방법 2: Redis 기반 대기열 (현실적 선택)

Redis의 List나 Sorted Set을 큐로 사용합니다. 이 프로젝트에 이미 Redis가 있어서 도입이 쉽습니다.

```
[학생] → POST /enrollments
         └→ Redis LPUSH queue:course:1 "{student_id: 42, ...}"
         └→ Redis ZADD queue:course:1 {timestamp} {student_id}  ← 순서 보장
         └→ "대기번호 523" 즉시 응답

[FastAPI 백그라운드 워커 or Celery]
  └→ Redis RPOP queue:course:1  ← 선착순으로 꺼냄
  └→ 실제 DB 수강신청 처리 (SELECT FOR UPDATE)
  └→ 결과를 Redis 또는 DB에 저장

[학생] → GET /queue/523
         └→ Redis에서 결과 조회 → "처리 중 (앞에 12명)" or "성공"
```

**장점**: 빠름, 순서 보장, 인메모리라 조회도 빠름
**단점**: Redis 장애 시 대기열 소실 위험

---

### 방법 3: WebSocket 실시간 대기열 (UX 최고)

HTTP 폴링 대신 WebSocket으로 연결을 유지하면서 순번과 결과를 실시간 푸시합니다.

```
[학생] → WebSocket 연결 + 수강신청 요청
         └→ 서버: "현재 523번째, 앞에 522명"
         └→ 서버: "앞에 100명" (실시간 업데이트)
         └→ 서버: "수강신청 완료!" or "정원 초과"
[학생] ← 연결 종료
```

**장점**: 실시간 순번 표시 (수능 원서접수 같은 UX)
**단점**: 구현 복잡, 연결 수 관리 필요

---

## 매크로 방지 + 서버 부하 동시 해결

대기열 시스템에 이런 장치를 함께 넣습니다.

```
[요청 진입 시]
  1. 토큰 검증 (JWT) → 본인 확인
  2. 중복 대기열 체크 → 같은 학생이 같은 강의에 이미 대기 중이면 거부
  3. 대기열 총량 제한 → 큐가 1,000개 넘으면 "마감" 응답
  4. 진입 토큰 발급 → 대기열에 들어온 학생에게만 고유 토큰 발급
                       → 이 토큰 없이 결과 조회 불가

[대기열 처리 시]
  5. 처리 속도 제한 → 초당 N건만 꺼내서 처리 (DB 보호)
  6. 타임아웃 → 일정 시간 내 처리 안 되면 자동 취소
```

---

## 이 프로젝트에 적용한다면

현재 구조와 가장 잘 맞는 건 **Redis 기반 (방법 2)** 입니다.

```
현재: 요청 → FastAPI → DB (동기적, 동시성 폭발)

개선: 요청 → Redis 큐 → 워커가 순서대로 처리 → DB
              ↑
         이미 Redis 사용 중이므로 추가 인프라 불필요
```

수강신청처럼 **선착순**이 중요한 시스템은 Redis Sorted Set에 `신청 시각`을 score로 넣으면 접수 순서도 공정하게 보장할 수 있습니다.

## 방법별 비교

| 항목 | DB 기반 | Redis 기반 | WebSocket |
|------|---------|-----------|-----------|
| 구현 난이도 | 낮음 | 중간 | 높음 |
| 실시간성 | 낮음 (폴링) | 중간 (폴링) | 높음 (푸시) |
| 추가 인프라 | 불필요 | Redis 필요 | Redis + WS |
| 장애 시 데이터 | DB에 영속 | 소실 위험 | 소실 위험 |
| 처리 속도 | 느림 | 빠름 | 빠름 |
| 선착순 보장 | 가능 | 가능 | 가능 |
